# 05 — User phone, $unset clears, phoneToRecipient

Decision: D8, D9, D10, D7. Depends on: 04. Blocks: 08.

## Goal

Users have an optional validated `phone`, settable and clearable through `PATCH /users/me` and `PATCH /users/:id`.
Both update paths clear `phone` and `avatarUrl` with `$unset` through `setOrUnset`, and `phoneToRecipient(phone)`
turns a stored phone into the string `SmsProvider` expects.

- `src/lib/mongo/schemas/user.schema.ts` — existing: `phoneSchema` sub-schema + `phone` field
- `src/lib/mongo/zod/user.dto.ts` — generated by `bun sync`, never hand-edited
- `src/user/user.request.dto.ts` — existing: `phoneUpdateSchema` in `UpdateUserDto` and `UpdateMeDto`
- `src/user/user.service.ts` — existing: `updateUser` / `updateMe` build the update with `setOrUnset`

- `AGENTS.md` — existing: Notifications section only

## Steps

1. Schema (D8): add `phoneSchema` with `createSubSchema` (from `lib/util/Constants.ts`) and
   `phone: { type: phoneSchema, required: false }` after `avatarUrl`. No index, not unique.
2. Run `bun sync`. Confirm `user.dto.ts` now has `phone` and that `UserZodSchema.shape.phone` unwraps the way
   the request DTO expects.
3. Request DTOs (D8): add `phoneUpdateSchema`, built from the generated shape, nullable, with the validation
   rules from the decision. Use a generic example in the country-code message (e.g. `+1`). Add `phone` to both
   `updateUserSchema` and `updateMeSchema`.
4. Service (D9, D7): in `updateUser` and `updateMe`, collect scalar fields (`name`, `email`, `role`, `status`,
   `phone`, and the resolved `avatarUrl`, which is `null` when removed) into one object and pass
   `setOrUnset(...)` to `updateOne`. Keep the existing rules: `email: null` is ignored, not cleared (email is
   required); non-`Accepted` status still sets `sessions: []`; email conflict check stays. A field absent from
   the body must stay untouched. If `updateOne` doesn't take operator updates (see task 04's report), say so in
   the report and use the model's `findOneAndUpdate` through the existing base-service method that does.
5. Check that the response DTOs (`userBaseSchema` omits from `UserZodSchema`) now include `phone`. They should,
   because they derive from the generated schema. Check that `diffObjects` in the audit entry still reports the
   change when a field is unset.
6. `phoneToRecipient(phone: { countryCode: string; number: string }): string` returns
   `countryCode.replace(/^\+/, '') + number` (D10). JSDoc example: `{ countryCode: '+1', number: '5550100' }` → `'15550100'`.
7. AGENTS.md Notifications: add a line that `user.phone` is `{ countryCode, number }`, so call
   `sendSmsAndEmail({ phone: user.phone && phoneToRecipient(user.phone), email: user.email }, …)`.
8. E2E in `tests/app.e2e-test.ts`:
   - `PATCH /users/me { phone: { countryCode: '+1', number: '5550100123' } }` → 200, then `GET /users/me` includes that phone.
   - `PATCH /users/me { phone: null }` → 200; then the stored doc has no `phone` key
     (`(await users.model.findOne({ email }).lean())` has no `phone` property), and `GET /users/me` has no `phone`.
   - Invalid cases → 400: `countryCode: '1'`, `number: '55a'`, total digits 7, total digits 16.
   - `PATCH /users/me { name: 'X' }` leaves an existing phone untouched.
